# 사전 검사 2단계의 검사 단위를 짝에서 파일 클러스터로 바꾼다

> 부모 설계: [feature-plan-preflight/design-doc.md](../feature-plan-preflight/design-doc.md)
> 이 문서는 그 설계의 **D2 · D9 · D25 를 개정**한다. 나머지 결정은 그대로 유지된다.

## 문제 정의

`/preflight` 2단계는 검사 단위를 **태스크 짝**으로 정의한다 (`overlappingPairs`).
같은 파일을 쓰는 태스크가 n 개면 짝이 `n(n-1)/2` 개 생기고, 짝마다 opus 에이전트
1개가 뜬다.

부모 플랜(태스크 15개)으로 **실측**했다:

```
현재 짝  : 39
  9개 태스크가 controller/preflight.ts 를 쓴다  → 짝 36개
  3개 태스크가 controller/contract.ts 를 쓴다   → 짝  3개
```

**36개가 같은 질문의 반복이다** — "태스크 A 와 B 가 `preflight.ts` 에서 충돌하는가".
한 파일을 순차로 확장하는 것은 정상적인 플랜 형태이므로 이 36번은 거의 전부 노이즈다.

비용만의 문제가 아니다. 세 가지가 함께 망가진다:

| | 증상 |
|---|---|
| **비용** | 에이전트 39개 · 동시성 상한 6 에서 7 웨이브 |
| **사람의 처리 부담** | 에이전트마다 자기 `id` 를 만들고 `assembleResult` 는 `id` 로만 중복을 제거한다. `D13` 이 일괄 승인을 금지하므로 뜨거운 파일 하나의 진짜 충돌이 **같은 내용의 질문을 여러 번** 만든다 |
| **읽을 수 없는 보고** | `examined[]` 가 39줄이 된다. 부모 설계 D9 가 "자세히 — 무엇을 봤는지까지"를 고른 것이 여기서 자기 목적을 잃는다 |

근본 원인은 **검사 단위를 "기계가 공짜로 아는 것"으로 골랐다**는 것이다. 기계는 짝을
공짜로 안다. 그런데 사람이 알고 싶은 것은 "이 파일을 여러 태스크가 어떻게 나눠 쓰는가"다.

## 전제

- 부모 기능은 이미 머지됐다 (PR #1). 이 변경은 **작동하는 코드의 개정**이다.
- `**Files:**` 의 `Create`/`Modify` 파싱(`parseFiles`)은 그대로 쓴다. 검증된 층이다.
- Test 파일을 제외하는 현재 규칙을 유지한다 — 두 태스크가 같은 테스트 파일에
  케이스를 추가하는 것은 정상이고 모순 신호가 아니다.
- 1단계(관계 그래프)는 **건드리지 않는다.** 결정론적이고 폭발하지 않는다
  (선언된 관계 41개 = `examined_stage1` 41개).
- 이 변경 이전에 `/preflight` 가 실제로 완주한 적이 **없다.** 워크플로우 스크립트는
  기계 검사가 0인 파일이고 정독으로만 검증됐다. 즉 이 변경의 검증에는 **실제 1회
  실행**이 포함되어야 한다.

## 스코프 / 비스코프

### 스코프

1. `overlappingClusters(tasks): FileCluster[]` — 파일별로 2개 이상 태스크가 쓰는
   묶음을 낸다. `overlappingPairs` 를 대체한다.
2. 클러스터 단위 결함 판정 — `concernsUnit` 의 규칙을 부분집합 관계로 바꾼다.
3. 워크플로우가 클러스터마다 에이전트 1개를 띄운다. 프롬프트가 "이 파일을 쓰는
   N 개 태스크 **사이의** 충돌을 찾아라"로 바뀐다.
4. `ExaminedUnit.kind` 에서 죽은 멤버 `"pair"` 를 제거한다.
5. 큰 클러스터에 `warn` 을 낸다 — 한 파일을 12 개 넘는 태스크가 쓰면 플랜 구조
   자체의 신호다.
6. **실제 `/preflight` 1회 실행** — 이 플랜 자신에 대해 돌려 워크플로우가 처음으로
   동작하는 것을 관찰한다.

### 비스코프

- 1단계 검사기 수정. 폭발하지 않으므로 손대지 않는다.
- 완결성 검사관(D17) 수정. 클러스터와 무관하게 플랜 전체를 본다.
- `--apply` 패치 적용 층. 결함의 **모양**은 바뀌지 않는다 (`task_ids` 2개 이상).
- 프롬프트 품질 튜닝. 첫 실제 실행 관찰 **후에** 판단할 일이다.
- 동시성 상한 조정. 클러스터 2개면 상한이 무의미하다.

## 제약

- **하드룰 #4** — 경계는 파일 + JSON 스키마다. 클러스터 프롬프트도 `kind` 를 포함한
  필수 필드를 못박아야 한다 (부모 6회전 리뷰가 잡은 결함).
- **하드룰 #3** — 모든 `agent()` 에 `model` 을 명시한다.
- **설계 D13** — 일괄 승인을 만들지 않는다. 클러스터가 결함을 여러 개 내면 여전히
  하나씩 묻는다. 클러스터화는 **질문 수를 줄이는 것이 아니라 중복 질문을 없애는 것**이다.
- **설계 D25** — 커버리지는 "무엇을 봤는지"를 정확히 센다. 클러스터로 바꾸면
  `examined_stage2` 의 단위가 바뀌므로 그 의미를 필드 주석에 적어야 한다.
- `workflows/*.js` 는 tsconfig 밖이고 실행 테스트가 불가능하다. 기계 검사는 문자열
  단언뿐이므로 **정독 + 실제 실행**이 유일한 검증이다.
- 짝을 하나도 잃지 않아야 한다. 검산: 클러스터의 `n(n-1)/2` 합계가 현재 짝 수와 같다
  (실측 36 + 3 = 39 ✓).

## 수용 기준

1. `overlappingClusters` 가 부모 플랜에서 **클러스터 2개**를 낸다
   (`preflight.ts` 9개 · `contract.ts` 3개).
2. 모든 짝이 어떤 클러스터에 포함된다 — 태스크 짝 집합이 보존된다.
3. 클러스터 안의 2개 태스크만 지명한 결함이 그 클러스터를 `"defect"` 로 표시한다.
   무관한 태스크가 낸 결함은 그 클러스터를 오염시키지 않는다.
4. `ExaminedUnit.kind` 에 `"pair"` 가 없고, `"cluster"` 를 실제로 생산한다.
5. 12 개 넘는 태스크가 한 파일을 쓰면 `warn` 이 나온다. `error` 가 아니다 —
   검사기가 일을 거부하지 않는다.
6. `bun run typecheck` · `bun test` · `bun run check` 통과.
7. **`/preflight` 를 이 플랜에 실제로 돌려 `preflight.json` 이 생긴다.** 판정이
   무엇이든(CLEAN·REJECTED·BLOCKED) 워크플로우가 끝까지 돌아 스키마에 맞는 파일을
   남긴 것이 이 기준의 내용이다.

## 아키텍처 결정

### DC1. 클러스터의 단위는 **파일 하나**다 — 연결 성분이 아니다

`preflight.ts` 와 `contract.ts` 를 둘 다 쓰는 태스크가 있으면 두 파일은 그래프상
연결된다. 연결 성분으로 묶으면 클러스터가 1개가 되고 태스크 10개가 한 프롬프트에
들어간다.

**파일 단위로 자른다.** 사람이 검토하는 단위가 파일이고("이 파일을 누가 어떻게
나눠 쓰나"), 같은 태스크가 두 클러스터에 나오는 것은 문제가 아니다.

대가: 두 파일을 함께 건드려야만 드러나는 충돌은 두 프롬프트로 쪼개진다. 그것은
완결성 검사관(D17)이 플랜 전체를 보는 층에서 잡는다 — 그래서 D17 을 남겨 뒀다.

### DC2. 결함이 클러스터를 오염시키는 규칙은 **부분집합**이다

부모 코드의 규칙:

```ts
defects.some((d) => unitTaskIds.every((id) => d.task_ids.includes(id)))
```

짝(2개)에서는 맞다 — 결함이 그 두 태스크를 다 지명해야 그 짝의 결함이다.
클러스터(9개)에서는 **원리적으로 성립하지 않는다.** 결함이 9개를 다 지명하는 일은
없으므로 모든 클러스터가 영원히 `"clean"` 이 된다 — 거짓 음성이다.

**방향을 뒤집는다:**

```ts
defects.some((d) => d.task_ids.every((id) => unitTaskIds.includes(id)))
```

결함이 지명한 태스크가 **전부 이 클러스터 안**이면 이 클러스터의 결함이다.

> 부모 6회전이 이 함수를 한 번 고쳤다 — 원래는 결함들의 **합집합**으로 판정해서
> 무관한 이유로 결함이 된 태스크의 깨끗한 관계까지 `"defect"` 로 표시했다.
> 그때 얻은 교훈이 *"결함은 본질적으로 관계다"* 였고, 지금은 그 관계의 **크기**가
> 2 에서 n 으로 늘어난 것이다. 규칙을 크기에 의존하지 않게 다시 쓴다.

1단계 `"relation"` 단위는 항상 2개이므로 두 규칙이 같은 답을 낸다. 그래도 한 함수로
합친다 — 두 규칙을 유지하면 어느 것이 어디 쓰이는지가 곧 드리프트가 된다.

### DC3. 프롬프트는 클러스터를 **한 번에** 본다

짝 프롬프트: "태스크 A 와 B 가 `f` 에서 충돌하는가"
클러스터 프롬프트: "태스크 A·B·C…가 `f` 를 순차로 확장한다. 이 중 **충돌하는 짝**을 찾아라"

두 번째가 정보가 더 많다. 짝 프롬프트는 A·B 만 보므로 "C 가 나중에 같은 함수를
다시 고친다"를 모른다. **클러스터는 그 파일의 전체 이력을 본다.**

결함 보고에서 `task_ids` 는 여전히 **충돌하는 태스크만** 지명한다 — 클러스터 전체를
지명하지 않는다. 그래야 DC2 의 부분집합 판정과 `--apply` 의 패치 대상이 정확해진다.

### DC4. `"pair"` 를 유니온에서 **제거한다**

아무것도 생산하지 않는 유니온 멤버는 미완성 설계의 표식이다. 부모 6회전이 정확히
그 이유로 미사용 `"cluster"` 를 지적했다. 같은 것을 반대 방향으로 남기지 않는다.

낡은 `preflight.json` 이 `"pair"` 를 담고 있으면 스키마 검증이 거부한다. 게이트가
`plan_sha256` 일치를 요구하므로 낡은 파일은 어차피 거부된다 — 새 문제를 만들지 않는다.

### DC5. 큰 클러스터는 `warn` 이다 — `error` 가 아니다

12 개 넘는 태스크가 한 파일을 쓰면 프롬프트에 태스크 본문 12개가 들어간다.
상한을 두고 자르면 짝의 조합 문제가 되돌아오고, `error` 로 막으면 검사기가 일을
거부한다.

**경고만 낸다.** 그것 자체가 사람에게 유용한 신호다 — "이 파일을 15개 태스크가 쓴다"
는 플랜 구조를 다시 보라는 뜻이다. 에이전트가 프롬프트 크기로 실패하면 기존 실패
경로(`not_examined`)가 정직하게 기록한다.

12 이라는 수는 부모 플랜의 최대 클러스터(9)보다 크고, 프롬프트가 수천 줄이 되는
지점보다는 작게 고른 값이다. 상수 하나이므로 실측 후 조정한다.
