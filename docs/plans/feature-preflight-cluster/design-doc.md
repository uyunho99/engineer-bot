# 사전 검사 2단계의 검사 단위를 짝에서 파일 클러스터로 바꾼다

> 부모 설계: [feature-plan-preflight/design-doc.md](../feature-plan-preflight/design-doc.md)
> 이 문서는 그 설계의 **D2 · D9 · D25 를 개정**한다. 나머지 결정은 그대로 유지된다.

## 문제 정의

`/preflight` 2단계는 검사 단위를 **태스크 짝**으로 정의한다 (`overlappingPairs`).
같은 파일을 쓰는 태스크가 n 개면 짝이 `n(n-1)/2` 개 생기고, 짝마다 opus 에이전트
1개가 뜬다.

부모 플랜(태스크 15개)으로 **실측**했다:

```
현재 짝  : 39
  9개 태스크가 controller/preflight.ts 를 쓴다  → 짝 36개
  3개 태스크가 controller/contract.ts 를 쓴다   → 짝  3개
```

**36개가 같은 질문의 반복이다** — "태스크 A 와 B 가 `preflight.ts` 에서 충돌하는가".
한 파일을 순차로 확장하는 것은 정상적인 플랜 형태이므로 이 36번은 거의 전부 노이즈다.

비용만의 문제가 아니다. 세 가지가 함께 망가진다:

| | 증상 |
|---|---|
| **비용** | 에이전트 39개 · 동시성 상한 6 에서 7 웨이브 |
| **사람의 처리 부담** | 에이전트마다 자기 `id` 를 만들고 `assembleResult` 는 `id` 로만 중복을 제거한다. `D13` 이 일괄 승인을 금지하므로 뜨거운 파일 하나의 진짜 충돌이 **같은 내용의 질문을 여러 번** 만든다 |
| **읽을 수 없는 보고** | `examined[]` 가 39줄이 된다. 부모 설계 D9 가 "자세히 — 무엇을 봤는지까지"를 고른 것이 여기서 자기 목적을 잃는다 |

근본 원인은 **검사 단위를 "기계가 공짜로 아는 것"으로 골랐다**는 것이다. 기계는 짝을
공짜로 안다. 그런데 사람이 알고 싶은 것은 "이 파일을 여러 태스크가 어떻게 나눠 쓰는가"다.

## 전제

- 부모 기능은 이미 머지됐다 (PR #1). 이 변경은 **작동하는 코드의 개정**이다.
- `**Files:**` 의 `Create`/`Modify` 파싱(`parseFiles`)은 그대로 쓴다. 검증된 층이다.
- Test 파일을 제외하는 현재 규칙을 유지한다 — 두 태스크가 같은 테스트 파일에
  케이스를 추가하는 것은 정상이고 모순 신호가 아니다.
- 1단계(관계 그래프)는 **건드리지 않는다.** 결정론적이고 폭발하지 않는다
  (선언된 관계 41개 = `examined_stage1` 41개).
- 이 변경 이전에 `/preflight` 가 실제로 완주한 적이 **없다.** 워크플로우 스크립트는
  기계 검사가 0인 파일이고 정독으로만 검증됐다. 즉 이 변경의 검증에는 **실제 1회
  실행**이 포함되어야 한다.

- **2026-09-04 개정.** 초판을 `/preflight` 에 돌려 **결함 9건으로 반송당했다.** 그 9건을
  전부 요건으로 흡수한 것이 이 판이다. 반송 기록은
  [preflight-raw.json](preflight-raw.json) 에 있다. 초판이 놓친 것의 요약:
  배선 파일 누락(Ⓐ) · 판정이 파일을 버림(Ⓑ) · 방향 역전이 1단계를 깨뜨림(Ⓒ) ·
  경고를 담을 자리 없음(Ⓓ) · 세는 대상이 다름(Ⓔ).

## 스코프 / 비스코프

### 스코프

1. `overlappingClusters(tasks): FileCluster[]` — 파일별로 2개 이상 태스크가 쓰는
   묶음을 낸다. `overlappingPairs` 를 대체한다.
2. `concernsUnit` 을 **단위 종류로 갈라진** 판정으로 바꾼다 (DC2).
3. `PreflightResult.warnings` 필드를 신설하고 큰 클러스터 경고를 거기 싣는다 (DC5).
4. `preflight-raw.json` 의 `units_examined` 를 **`{kind, label}` 객체 배열**로 바꾼다 (DC6).
5. `assembleResult` 가 클러스터 단위를 만든다. `ExaminedUnit.kind` 에서 죽은 `"pair"` 제거.
6. **`controller/preflight-cli.ts` 배선** — `--plan` 이 `clusters` 를 내보내고,
   `--record` 가 경고를 `preflight.json` 에 싣는다 (DC7).
7. 워크플로우가 클러스터마다 에이전트 1개를 띄운다.
8. **실제 `/preflight` 재실행** — 이 플랜 자신에 대해 돌려 `CLEAN` 을 확인한다.

### 비스코프

- 1단계 검사기(관계 그래프) 수정. 폭발하지 않으므로 손대지 않는다.
- 완결성 검사관 프롬프트 수정. 플랜 전체를 보는 층은 그대로 둔다 —
  **초판 반송 9건 중 4건을 이 층이 찾았다.** 건드릴 이유가 없다.
- `--apply` 패치 적용 층. 결함의 모양(`task_ids` 2개 이상)은 바뀌지 않는다.
- 프롬프트 품질 튜닝. 첫 실제 실행을 관찰한 뒤에 판단할 일이다.
- 동시성 상한 조정. 클러스터 2개면 상한이 무의미하다.

## 제약

- **하드룰 #4** — 경계는 파일 + JSON 스키마다. **문자열 접두사로 종류를 알아내지 않는다** —
  이것이 DC6 이 배열의 원소를 객체로 바꾸는 이유다.
- **하드룰 #3** — 모든 `agent()` 에 `model` 을 명시한다.
- **설계 D13** — 일괄 승인을 만들지 않는다. 클러스터화는 질문 수를 줄이는 것이 아니라
  **중복 질문을 없애는 것**이다.
- **설계 D25** — 커버리지는 "무엇을 봤는지"를 정확히 센다. 초판이 이것을 어겼다(Ⓔ).
- `workflows/*.js` 는 tsconfig 밖이고 파일을 **읽지도 쓰지도** 못한다 (AMENDMENTS B7).
  기계 검사는 소스 문자열 단언뿐이므로 정독 + 실제 실행이 유일한 검증이다.
- **짝을 하나도 잃지 않아야 한다.** 검산: 클러스터의 `n(n-1)/2` 합계가 현재 짝 수와 같다
  (실측 36 + 3 = 39 ✓).
- 테스트는 `controller/preflight.test.ts` 에 append 한다. 여러 태스크가 공유하는 파일이므로
  **모듈 스코프 이름을 새로 선언하기 전에 이미 있는지 확인한다** — 중복 선언은 파일 전체를
  로드 불가로 만든다 (부모 5회전 반송 사유).

## 수용 기준

1. `overlappingClusters` 가 부모 플랜에서 **클러스터 2개**를 낸다
   (`preflight.ts` 태스크 9개 · `contract.ts` 태스크 3개).
2. 모든 짝이 어떤 클러스터에 포함된다 — 태스크 짝 집합이 보존된다.
3. **같은 `task_ids`, 다른 `file` 인 클러스터 2개에서, 한쪽에서만 나온 결함이 다른 쪽을
   오염시키지 않는다** (Ⓑ 회귀 테스트).
4. **1단계 `relation` 단위의 판정이 개정 전과 글자 그대로 같다** — 원소 1개짜리 단위와
   태스크 3개를 지명한 결함까지 포함해서 (Ⓒ 회귀 테스트).
5. `preflight.json` 에 `warnings` 배열이 있고, 13개 태스크가 한 파일을 쓰면 거기에
   `warn` 1건이 들어간다. 경고가 없으면 `[]` 다 — 필드 누락이 아니다 (Ⓓ).
6. `relations.examined_stage2` 가 **클러스터 수와 정확히 같다.** 서명 후보와 완결성
   검사관이 그 수를 부풀리지 않는다 (Ⓔ).
7. `bin/preflight <branch> --plan` 의 출력에 `clusters` 가 있고 `pairs` 가 없다.
   `overlappingPairs` 는 소스에서 사라진다 — 죽은 코드를 남기지 않는다 (Ⓐ).
8. `bun run typecheck` · `bun test` · `bun run check` 통과.
9. **`/preflight` 재실행이 `CLEAN` 을 낸다.**

## 아키텍처 결정

### DC1. 클러스터의 단위는 **파일 하나**다 — 연결 성분이 아니다

`preflight.ts` 와 `contract.ts` 를 둘 다 쓰는 태스크가 있으면 두 파일은 그래프상
연결된다. 연결 성분으로 묶으면 클러스터가 1개가 되고 태스크 10개가 한 프롬프트에 들어간다.

**파일 단위로 자른다.** 사람이 검토하는 단위가 파일이다 — "이 파일을 누가 어떻게 나눠 쓰나".

**그 대가를 초판이 처리하지 않았다:** 같은 태스크가 **여러 클러스터에 중복 소속되는 것이
정상 상태**가 된다. 초판은 이 문장을 설계 문서에 써 놓고도 판정 함수 서명에서 파일을
버렸다 — DC2 가 그것을 고친다.

두 파일을 함께 건드려야만 드러나는 충돌은 두 프롬프트로 쪼개진다. 그것은 완결성
검사관(D17)이 플랜 전체를 보는 층에서 잡는다.

### DC2. 판정 규칙은 단위의 **종류**로 가른다 — 크기로 가르지 않는다

초판은 `concernsUnit` 의 부분집합 방향을 **무조건** 뒤집으려 했다. 그것이 1단계를 두
방향으로 깨뜨린다:

| 단위 | 초판이 만드는 결과 |
|---|---|
| 원소 **1개**짜리 relation (`from Task N` 없는 `Consumes`) | 결함은 최소 2개를 지명하므로(D27) 1개짜리 단위의 부분집합이 될 수 없다 → **영원히 `clean`** |
| 원소 2개짜리 relation + 태스크 3개를 지명한 결함 `{1,3,5}` | 개정 전 `{1,3}` 은 `defect` 였는데 뒤집으면 `clean` → **회귀** |

둘 다 거짓 음성이고, `checkDefectShape` 의 주석이 *"이 기능에서 가장 위험한 방향"* 이라고
못박은 바로 그것이다.

**해결 — 하나의 함수가 단위를 통째로 받고 `kind` 로 분기한다:**

```
concernsUnit(defects, unit: { kind, task_ids, file? })

  kind === "relation"  →  unit.task_ids ⊆ d.task_ids     (개정 전 규칙 그대로)
  kind === "cluster"   →  d.task_ids ⊆ unit.task_ids     (뒤집은 규칙)
                          단, 그 전에 파일로 먼저 거른다
```

크기(`length === 1`)로 가르지 않는 이유: 클러스터도 원소가 2개일 수 있고 relation 도
2개다. **크기는 종류를 구분하지 못한다.** 종류는 호출자가 이미 알고 있으므로 넘기면 된다.

초판의 "두 규칙을 유지하면 드리프트가 된다"는 걱정은 **함수를 하나로 유지하고 분기를
그 안에 두는 것**으로 해소된다 — 두 함수를 만들지 않는다.

### DC3. 결함은 자기가 나온 **파일**을 들고 다닌다

DC1 이 중복 소속을 정상으로 만들었으므로, `task_ids` 만으로는 결함이 어느 파일에서
나왔는지 복원할 수 없다. `PreflightDefect` 에 **`file?: string`** 을 더한다 — 기존 필드에
옵셔널 추가라 하위 호환이다.

클러스터 판정은 **판정 이전에** 파일로 거른다: `unit.file` 과 `d.file` 이 둘 다 있고
서로 다르면 그 결함은 세지 않는다. `d.file` 이 없는 결함(1단계 관계 등 파일 개념이 없는
단위)은 거르지 않는다 — 과다 표시 쪽으로 안전하게 둔다.

워크플로우의 클러스터 프롬프트가 `file` 을 **반드시 채우게** 못박는다 (하드룰 #4 —
필수 필드를 모델의 암묵적 추론에 맡기지 않는다).

### DC4. 프롬프트는 클러스터를 **한 번에** 본다

짝 프롬프트: "태스크 A 와 B 가 `f` 에서 충돌하는가"
클러스터 프롬프트: "태스크 A·B·C…가 `f` 를 순차로 확장한다. 이 중 **충돌하는 짝**을 찾아라"

두 번째가 정보가 더 많다. 짝 프롬프트는 A·B 만 보므로 "C 가 나중에 같은 함수를 다시
고친다"를 모른다. **클러스터는 그 파일의 전체 이력을 본다.**

결함 보고의 `task_ids` 는 여전히 **충돌하는 태스크만** 지명한다 — 클러스터 전체를
지명하지 않는다. 그래야 DC2 의 부분집합 판정과 `--apply` 의 패치 대상이 정확해진다.

### DC5. 경고에는 **담을 자리**가 있어야 한다

`oversizedClusterWarnings` 가 `Violation[]` 을 내는데 `PreflightResult` 에 그것을 담을
필드가 없으면 **생산되자마자 버려진다.** 초판이 그 상태였고, "경고는 `--record` 단계에서
컨트롤러가 낸다"고 미룬 곳(`preflight-cli.ts`)은 범위에 들어 있지도 않았다.

`PreflightResult.warnings: Violation[]` 을 신설한다. 값이 없으면 `[]` 다 — `undefined`
나 필드 누락이 아니다. 콘솔 문자열로 흘리는 우회는 하드룰 #4(자유 텍스트 파싱 금지)에
막힌다.

**`warn` 은 판정을 바꾸지 않는다.** `verdict` 는 결함 수로만 정해진다 — 검사기가 일을
거부하지 않는다는 것이 이 결정의 요점이다.

12 라는 수는 부모 플랜의 최대 클러스터(9)보다 크고, 프롬프트가 수천 줄이 되는 지점보다는
작게 고른 값이다. 상수 하나이므로 실측 후 조정한다.

### DC6. `units_examined` 는 **객체 배열**이다 — 문자열 접두사로 종류를 알아내지 않는다

`examined_stage2` 는 `raw.stage2.units_examined.length` 로 계산되는데, 그 배열에는
클러스터 단위 말고도 서명 후보(`sig:<id>`)와 완결성 검사관(`critic`)이 **같이** 들어간다.
따라서 실제 값은 `서명 후보 + 클러스터 + 1` 이다. 초판은 이것을 모른 채 "클러스터 수를
센다"를 요건으로 적었다 — **픽스처에서만 참이고 실제 파이프라인에서는 항상 거짓**이었다.

실측 증거: 2026-09-04 실행에서 검사 단위 6개인데 `units_examined` 가 7개였다.

접두사(`sig:`)로 걸러내는 우회는 하드룰 #4 위반이다 — 자유 텍스트를 파싱하게 된다.
**원소를 `{ kind: "signature" | "cluster" | "critic", label: string }` 객체로 바꾼다.**
`checkPreflightRaw` 가 그 모양을 강제하고, `relationCoverage` 는 `kind === "cluster"` 만
센다.

D25 가 "커버리지는 무엇을 봤는지 정확히 센다"를 규정한 이유가 이것이다. 숫자가 부풀면
`examined_stage2 === clusters.length` 라는 안심이 거짓이 된다.

### DC7. `controller/preflight-cli.ts` 는 **범위 안**이다

초판이 놓친 가장 큰 것. 이 파일은 세 가지의 유일한 지점이다:

- `overlappingPairs` 의 **유일한 호출자** (66행 · 104행)
- 워크플로우가 읽는 `args.pairs` 의 **유일한 생산자** (`--plan` 출력)
- `assembleResult` 의 **유일한 호출자**

범위에서 빼면 세 가지가 동시에 깨진다:

| | 증상 |
|---|---|

(c) 가 가장 위험하다. 조용히 통과 도장을 찍는다.

어느 쪽을 읽는지가 곧 드리프트가 된다.
