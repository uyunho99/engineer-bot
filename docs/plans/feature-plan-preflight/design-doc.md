해서 — 즉, 그 전에 다양한 시나리오에 대해서 철저하게 준비를 해야겠지."*

이 원칙이 이 문서의 대상을 정당화한다. **사전 검사기는 이 원칙의 첫 구현체다** — AI 여러 개를 미리
풀어 조사시키고, 사람에게는 정리된 결과만 준다. 기획 단계용 "논의 준비기"는 같은 패턴의 두 번째
구현체가 되며, 여기서 배운 구조를 재사용한다.

명세 §3.2가 `plan-ceo-review`를 "반대화형"으로 규정하며 쓴 문장과 같은 취지다 — *"사람 확인이
필요한 항목만 질문, 나머지는 자체 진행."* 6.2.0 SDD도 같은 패턴을 쓴다 (*"Present everything you
find as **ONE batched question**"*).

## 2. 문제 정의

`writing-plans`가 만든 `plan.md`에는 **할 일 사이의 모순**이 생긴다. 각 할 일은 개별적으로는
말이 되는데 서로 안 맞는 경우다.

```
Task 3: 전화번호는 숫자만 저장한다              → storage.ts
Task 7: 저장된 전화번호를 그대로 화면에 뿌린다   → display.ts
```

두 할 일은 각각 옳고, 파일도 다르다. 그런데 화면에 `01012345678`이 나온다.

**SDD는 이런 모순을 만나도 멈추지 않는다.** 순서대로 완주하는 것이 그 도구의 본질이다
(명세 §6.3). 모순은 Task 7쯤에서 리뷰어에게 잡히거나, 안 잡히면 PR까지 간다. 잡히더라도 그때는
이미 6개 할 일을 만든 뒤라 되돌리는 비용이 든다.

현재 `controller/contract.ts`의 계약 검증은 **형식만** 본다 — 필수 섹션 존재, `### Task N:` 헤딩
형식(B4), 2축 태그 유무, 번호 연속성. **내용의 모순은 보지 않는다.**

### 2.1 지금 이 결함이 발견되는 경로와 비용

| 발견 시점 | 경로 | 비용 |
|---|---|---|
| 빌드 시작 전 | **없음** | — |
| Task 1 디스패치 직전 | 6.2.0 SDD의 pre-flight scan → 사람에게 질문 → 오버레이가 `REJECTED`로 변환 (A3) | 낮음. 단 세션 기동 비용은 이미 씀 |
| 빌드 도중 | task reviewer가 잡음 → 플랜 충돌 → `REJECTED` (A3-2) | **높음. 이미 만든 것을 버린다** |
| 안 잡힘 | PR에 모순이 실린 채 게이트 ②로 감 | 최악 |

AMENDMENTS A3이 첫 경로를 이렇게 평가했다:

> **빌드 시작 전이라 손실이 0이다. 이 경로가 가장 값싸다**

이 문서는 그 지점을 **게이트 ① 앞으로 한 칸 더 당긴다.**

### 2.2 부수 효과 — 6.2.0 유지 결정의 약점을 메운다

AMENDMENTS A7에서 superpowers를 **6.2.0(릴리스)** 에 고정하기로 했다. 6.3.0은 이 사전 스캔을
강화했지만(*"태스크 쌍마다 한 행, 각 태스크마다 한 행. 그 행들 없이 '스캔이 깨끗하다'는 것은 당신이
돌린 스캔이 아니다"*) 우리는 그 개선을 받지 않는다.

사전 검사기는 **스킬을 건드리지 않고 옆에서** 같은 값을 얻는다. 명세 P4(fork 금지)를 지키면서
6.3.0의 좋은 부분을 가져오는 유일한 경로다.

## 4. 스코프 / 비스코프

### 4.1 스코프 — 2단계로 나눈다

> **2026-09-03 개정 (Codex outside voice).** 초안은 AI에게 "주제로 묶어라"고 시켰다.
> 그런데 **계획서가 이미 자기 관계를 선언한다** — `overlay/writing-plans-tagging.md`가 정의하는
> `**Interfaces:** Consumes / Produces`가 그것이다. 초안은 그 선언을 쓰지 않고 AI에게 다시
> 찾게 시켰고, 그 결과 커버리지를 **관계**가 아니라 **태스크** 단위로 세는 오류까지 만들었다
> (구 D18). 아래처럼 나눈다: **기계가 선언된 관계를 전부 검사하고, AI가 선언되지 않은 것을 찾는다.**

**1단계 — 기계 (결정론적 · 무료 · 100% 테스트)**

1. **관계 그래프 추출** — 각 태스크의 `**Interfaces:**`에서 `Consumes`/`Produces`를 파싱해
   태스크 간 의존 그래프를 만든다
2. **매달린 참조** — `X from Task N`을 소비하는데 Task N의 `Produces`에 X가 없다 → **결함 확정**
3. **순서 위반** — 앞 태스크가 뒤 태스크의 산출을 소비한다 → **결함 확정**
4. **서명 불일치 후보** — 같은 심볼의 `Produces` 서명과 `Consumes` 서명이 텍스트로 다르다 →
   **확정하지 않고 2단계로 넘긴다** (표기만 다를 수 있다)
5. **파일 겹침 짝** — `**Files:**`에서 같은 파일을 건드리는 짝을 뽑는다

**2단계 — AI (선언되지 않은 것을 찾는다)**

6. **서명 후보 판정** — 1단계가 넘긴 후보가 진짜 불일치인지 판정
7. **미선언 관계 탐색** — 짝·묶음마다 AI 하나가 *"선언에 없지만 실제로 충돌하는 것"*을 찾는다.
   §2의 전화번호 예처럼 `Interfaces`에 안 적힌 암묵적 결합이 대상이다
8. **반증** — 발견마다 AI 하나가 반박을 시도한다. 반박에 실패한 것만 진짜 결함
9. **완결성 검사관** — 전체를 다시 보고 놓친 관계를 찾는다 (D17)

**3단계 — 사람 (게이트 ① 앞)**

10. **수정 제안** — 결함마다 구조화된 패치를 낸다 (D24)
11. **승인된 수정 적용** — 결함마다 채택/기각을 결정하고 채택분만 반영 (§6.4)
12. **재검사** — 반영 후 다시 검사한다 (D10)

**전 단계 공통**

13. **관계 단위 커버리지 보고** — 선언된 관계 몇 개 중 몇 개를 검사했는지, **검사하지 않은 관계가
    무엇인지** 기록한다 (D25). 태스크 단위로 세지 않는다
14. **기계 게이트** — `bin/builder`가 `preflight.json`을 읽고 통과하지 않은 플랜의 빌드를 거부한다
    (D26). 이것이 없으면 이 기능 전체가 강제되지 않는다
15. **자동 실행 장치** — `plan.md` 저장 시 형식 검사가 돌고, 내용 검사가 필요하면 알린다 (D23)
16. **중복 방지** — 같은 내용을 **유효한 `CLEAN`으로** 검사한 적이 있으면 건너뛴다 (D10)

**1단계만으로도 이 기능은 성립한다.** 2단계가 기대에 못 미쳐도 매달린 참조와 순서 위반은
잡힌다 — 그리고 그 둘이 SDD를 실제로 깨뜨리는 결함이다. 이것이 단계를 나눈 이유다.

| 안 하는 것 | 이유 |
|---|---|

| **설계문서 대조** (플랜이 design-doc과 어긋나는지) | 사용자가 "주제별 묶기"를 골랐다. 별도 기능으로 분리 |
| **코드 읽기** | 검사 대상은 `plan.md` 텍스트다. 레포 코드를 읽어 검증하지 않는다 |
| **`bin/builder` 안에서의 실행** | 게이트 ① 앞 전용. headless 세션에서는 6.2.0 SDD의 자체 스캔이 담당한다 (A3) |
| **기획 단계용 "논의 준비기"** | 같은 패턴의 다음 구현체. 이 문서 범위 밖 |
| **파일 수준 의존 검사** | `**Interfaces:**`는 **심볼 의존만** 표현한다. "Task 13 은 Task 11 이 만든 `bin/preflight` 파일에 의존한다" 같은 관계는 적을 자리가 없다. 파일 경로를 심볼로 적으면 `symbolName("bin/preflight")`가 `"bin"`이 되어 거짓 `dangling_ref`가 난다. **이 계획서를 쓰다가 실측으로 드러난 한계다.** 파일 의존은 산문에 적고, 순서는 플랜의 선형 순서가 강제한다. 넓히려면 `- Consumes: \`file:bin/preflight\` from Task 11` 같은 접두 규약이 필요하고, 그것은 별도 결정이다 |
| **기존 타입의 리터럴 유니온 확장** | `Consumes: `Violation`` 은 *"이 타입을 쓴다"* 까지만 말하고 *"이 타입의 `file` 필드가 내 파일명을 받아주는가"* 는 말하지 못한다. `**Interfaces:**` 그래프는 **심볼**을 모델링하고 **심볼의 필드 모양**은 모델링하지 않는다. 1단계 기계 검사는 원리적으로 못 잡고, 2단계 파일 겹침 짝도 못 잡는다 — 소비 태스크와 타입 정의 파일을 **함께** 건드리는 태스크가 없으면 짝이 만들어지지 않는다. **이 계획서가 4회전에서 정확히 이 결함으로 반송됐다 — 검사기의 자기 시연이다** (`Violation.file` 이 닫힌 유니온이라 `"preflight-raw.json"` 을 못 받았다). 알려진 사각지대로 남긴다 |
| **`state.sqlite` 연동** | §1.2에서 버렸다 |
| 태그(2축) 내용 검증 | 별개 관심사. 형식 검증은 이미 `contract.ts`에 있다 |

## 5. 제약

### 5.1 플랫폼 제약 — 설계를 강제하는 것

**워크플로우 스크립트는 파일시스템·Node API에 접근할 수 없다.**
(`workflow-authoring`: *"No filesystem or Node.js API access."*)

따라서 판단 로직은 **어차피 `controller/` 안에 있어야 한다.** 스크립트에는 `agent()` 호출과 결과
수집만 남는다. **테스트할 수 없는 부분이 테스트할 필요가 없는 부분과 정확히 일치한다.**

**`Workflow`는 툴이다.** 셸 스크립트가 호출할 수 없다. 그래서 실행이 3단계로 나뉜다 —
기계(CLI) → 에이전트(세션) → 기계(CLI). `/preflight` 스킬이 셋을 묶는다.

**훅은 셸 명령이다.** 훅에서 워크플로우를 부를 수 없다. 그래서 훅은 형식 검사만 돌리고, 내용 검사가
필요하면 **출력으로 세션에 알린다** (훅 출력은 사용자 피드백으로 취급된다).

**D23 — 훅은 `PostToolUse`다. 쓰기를 막을 수 있는 훅을 쓰지 않는다.**
쓰기 **전에** 도는 훅은 검사 실패로 `plan.md` 저장 자체를 막을 수 있다. `--gate`의 오탐 하나가
계획서 작성을 중단시키고, AI가 쓰던 내용을 되돌릴 방법이 없다. 검사기가 계획서 작성을 방해하는
것은 이 기능의 목적을 정면으로 뒤집는다.

훅은 **쓰기가 끝난 뒤** 돌고, 결과를 알림으로만 흘린다. `--gate`가 0이 아닌 종료 코드를 내도
파일은 이미 저장돼 있다. 이것이 §4.1-8("형식 검사가 돌고, 내용 검사가 필요하면 **알린다**")의
"알린다"가 뜻하는 바다 — 막는다가 아니다.

### 5.2 레포 제약

| 제약 | 출처 |
|---|---|
| 자유 텍스트 파싱 금지. 경계는 파일 + JSON 스키마. 파싱 실패는 성공이 아니라 `BLOCKED` | 하드룰 #4 |
| 계획서를 현장에서 고치지 않는다 → 반송. **적용 범위는 게이트 ① 이후**(빌드 중)다 | 하드룰 #2 · 명세 §6.3 |

| `git clean -fdx` 금지 | 하드룰 #5 |

### 5.3 도그푸딩 제약

이 기능은 **engineer-bot 자신**에 만든다. 그래서:

- `TARGET_REPO`가 하네스 레포 자신이다. `controller/paths.ts` 주석의 *"이 경로들은 제품 레포 기준이다.
  engineer-bot이 아니다"* 라는 전제가 이번에는 깨진다. **경로 계산은 실측으로 정상 동작을 확인했다**
  (`bun controller/paths.ts` → `docs/plans/feature-plan-preflight/`).
- `visible` 표면이 없다. 이번 회전에서 게이트 ②의 데모 경로는 검증되지 않는다. `invisible`-only
  보고 패킷 경로가 대신 검증된다.
- `controller/builder.ts`가 오버레이를 `HARNESS_ROOT`(= `import.meta.url`의 상위)에서 읽는다.
  SDD가 worktree를 만들면 **오버레이 원본과 worktree 사본이 갈릴 수 있다.** 1회전에서 관찰할 항목.

**D2 — ~~주제 묶기는 AI가, 파일 겹침은 기계가 한다~~ → 개정: 관계 그래프는 기계가, 미선언 충돌은 AI가.**

⚠️ **2026-09-03 개정 (§4.1).** 초안은 AI에게 "주제로 묶어라"고 시켰다. 계획서가 이미
`**Interfaces:**`로 관계를 선언하므로 **기계가 선언된 관계를 전부 검사하고, AI는 선언되지 않은
것만 찾는다.** AI의 주제 묶기 단계는 사라졌다.
"같은 주제"는 기계가 알 수 없다. "같은 파일"은 기계가 공짜로 안다. 둘은 서로를 보완한다 —
주제 묶기는 파일이 다른 모순(§2의 전화번호 예)을 잡고, 파일 겹침은 주제 묶기가 놓친 것을 잡는다.

**D3 — ~~묶음 하나가 8개를 넘으면 쪼갠다~~ → 폐기.**

⚠️ **2026-09-03 폐기.** D2 개정으로 **AI 주제 묶기 단계 자체가 없어졌으므로** 묶음 크기 상한도
대상이 사라졌다. 2단계의 검사 단위는 이제 파일 겹침 **짝**이며, 짝은 정의상 태스크 2개다.
`ExaminedUnit.kind`의 `"cluster"` 값은 나중에 묶음 개념이 돌아올 경우를 위해 남겨두지만
현재 쓰이지 않는다.

근거: 놓친 결함은 빌드 중 리뷰어가 잡는 2차 방어선이 있다. 잘못 반송한 것은 사람 시간을 쓰고,

담는다. "7번을 고치세요"가 아니라 "7번 할 일 본문에 이 줄을 추가하세요: `표시할 때 하이픈을 넣는다`".

### 6.3 계약 — 입력과 출력

조용한 실패를 초안의 형식 가정이 직접 만들어낸다.

| | 결정 |
|---|---|
| **채택** | 위 형식을 그대로 파싱한다. `- Create:` / `- Test:` 접두, 백틱 감싼 경로 |
| **`**Interfaces:**`를 필수로 올린다** | 지금은 오버레이의 **예시**일 뿐이고 `contract.ts`가 파싱하지 않는다. 1단계 기계 검사의 유일한 입력이므로 계약 필수 항목이 된다 |
| 파급 | **`controller/contract.test.ts`가 수정 대상에 들어간다.** 기존 정상 픽스처가 새 필수 항목(`Interfaces`)을 갖도록 고쳐야 한다 — 초안의 10파일 목록에 이것이 빠져 있었다 |

**D24 — 수정 제안은 자연어가 아니라 구조화된 패치다.**

초안은 `suggested_fix`에 "적용할 정확한 텍스트"를 담으라고만 했다. **그것으로는 적용할 수 없다** —
삽입인지 교체인지, 어느 태스크의 어느 위치인지가 없다. 그리고 `--apply d1`을 설계했는데
`Defect`에 `id`가 없었다.

```ts
export interface FixPatch {
  op: "insert_after" | "replace";
  task_id: string;          // 어느 태스크 안인지
  anchor: string;           // 그 태스크 본문에서 찾을 기준 문자열
  text: string;             // 넣거나 바꿀 내용 (바이트 그대로 — D14)
}
```

`anchor`는 **해당 태스크 본문 안에서만** 찾는다. 계획서 전체에서 찾으면 다른 태스크의 같은 줄에
매치된다 — D22가 다루던 다중 매치 문제의 절반이 이 범위 제한으로 사라진다. 태스크 안에서도
여럿이면 D22대로 사람에게 묻는다.

**D7 — 결과는 새 파일 `docs/plans/<slug>/preflight.json`이다.**
`build-result.json`에 합치지 않는다. 그것은 **빌드 결과**(A6: 세션 → 컨트롤러)이고 이것은
**빌드 전 검사**다. 쓰는 주체도 시점도 다르다.

**D8 — ~~결함 형식은 `defects[]`를 재사용한다~~ → D27이 뒤집었다.**

⚠️ **2026-09-03 정정.** 아래 본문은 초안의 논거이며 **더 이상 채택된 결정이 아니다.**
`PreflightDefect`는 전용 타입을 쓴다 — 사전 검사 결함은 본질적으로 관계이고, 선택 필드로는
스키마가 그것을 강제하지 못한다. **D27을 읽어라.** 공유하는 것은 표현(출력 형식)이지 타입이 아니다.

초안의 논거 (기록용):

```
task_id · plan_text(문제 있는 원문 인용) · conflict · suggested_fix
+ related_task_ids?: string[]     ← 이 문서에서 추가 (선택 필드)
```

**반송 경로가 하나가 된다.** 사람이 보는 화면이 사전 검사든 빌드 중 반송이든 같다.

**D20 — 익명 타입에 이름을 준다.** `contract.ts:346`의 `defects`는 지금 **익명 인라인 타입**이라
`import`할 수 없다. 이름을 빼내고 `BuildResult`가 그것을 참조하게 한다.

**D27 — 그러나 preflight는 `BuildDefect`를 재사용하지 않고 전용 타입을 쓴다.**

⚠️ **2026-09-03 정정. 초안(D8)의 "스키마 재사용"이 의미를 흐렸다.**
빌드 중 결함은 태스크 **하나**의 문제여도 된다 ("Task 5의 구현이 플랜과 다르다"). 사전 검사의
결함은 **본질적으로 관계**다 ("Task 3과 Task 8이 서로 안 맞는다"). 초안은 `related_task_ids`를
**선택 필드**로 뒀는데, 그러면 스키마가 "두 태스크가 충돌한다"를 강제하지 못한다 — §7의 전화번호
픽스처 수용 기준을 타입이 보증할 수 없다.

```ts
// 공통 조상 없음. 두 타입은 다른 것을 뜻한다.
export interface BuildDefect {          // 빌드 중 반송 (기존, 이름만 부여)
  task_id: string;
  plan_text: string;
  conflict: string;
  suggested_fix?: string;
}

export interface PreflightDefect {      // 사전 검사 (신규)
  id: string;                           // --apply 의 인자. 초안에 없었다 (D24)
  kind: "dangling_ref" | "order_violation" | "signature_mismatch" | "undeclared_conflict";
  task_ids: [string, string, ...string[]];  // 최소 2개. 타입이 관계를 강제한다
  relation?: string;                    // 어느 심볼/인터페이스 때문인지 (1단계 결함은 필수)
  plan_text: string;                    // 문제 있는 원문 인용
  conflict: string;
  patch?: FixPatch;                     // 구조화된 수정 (D24)
  stage: 1 | 2;                         // 기계가 잡았나 AI가 잡았나
}
```

`task_ids`의 튜플 타입이 **컴파일 시점에 최소 2개를 강제한다.** `stage` 필드가 있으므로
"기계가 확정한 것"과 "AI가 판단한 것"을 사람이 구분해서 볼 수 있다 — 1단계 결함은 반박할 여지가
없고, 2단계 결함은 오탐일 수 있다.

**반송 화면은 여전히 하나다.** `formatViolations`처럼 두 타입을 같은 형식으로 출력하는 함수를
공유한다 — 공유해야 하는 것은 **표현**이었고, 타입이 아니었다.

**D28 — 워크플로우 → `--record` 경계에 전체 스키마를 정의한다.**

⚠️ **2026-09-03 추가.** 초안은 *"스키마로 검증한다"(D11)*고만 쓰고 `defects[]` 밖의 계약을
정의하지 않았다. 그러면 세션이 워크플로우 반환값을 **텍스트로 옮겨 적는** 경로가 생기고,
그것은 하드룰 #4(파일 + JSON 스키마만이 경계)와 A6가 막으려던 바로 그 실패다.

워크플로우는 **파일에 쓴다.** 세션이 값을 옮기지 않는다:

```jsonc
// docs/plans/<slug>/preflight-raw.json  ← 워크플로우가 직접 쓴다
{
  "schema": 1,
  "plan_sha256": "…",              // 어느 플랜을 봤는지. --record 가 대조한다
  "stage1": { "relations_declared": 12, "defects": [...] },
  "stage2": { "units_examined": [...], "units_failed": [...], "defects": [...] },
  "critic": { "additional_defects": [...] }
}
```

`--record`가 이 파일을 읽어 검증하고 `preflight.json`으로 정규화한다.
`units_failed`가 비어 있지 않으면 그 관계는 `not_examined`로 간다 (D25).
`plan_sha256`이 현재 `plan.md`와 다르면 **`BLOCKED`** — 검사 도중 플랜이 바뀌었다는 뜻이다.

**D29 — `applied[]`는 재검사를 넘어 살아남는다.**

⚠️ **2026-09-03 추가.** 초안대로면 적용 후 재검사 시 `--record`가 새 `preflight.json`을 쓰면서
**이전 `applied[]`가 사라진다.** D15의 감사 기록이 첫 재검사에서 소멸한다.

`--record`는 기존 `preflight.json`이 있으면 `applied[]`를 **읽어서 이어붙인다.** 나머지 필드는
새 검사 결과로 교체한다. `applied[]`만 누적이다 — 그것이 "계획서가 왜 이렇게 바뀌었는지"의
유일한 기록이기 때문이다 (`git log`와 두 겹을 이룬다).

**D21 — `extractFiles`는 파일 시스템을 건드리지 않는다.** `**Files:**`에 적힌 경로는 대부분
**아직 존재하지 않는 파일**이다 — 계획서는 "이 파일을 만들 것"을 적은 문서다. 구현자가
`existsSync`로 거르면 **새로 만들 파일이 전부 사라지고 짝이 0개가 되어** 검사기가 조용히
아무것도 하지 않는다. `extractFiles`는 문자열 → 문자열 배열이며, 그래서 순수 함수다 (D1).

**D9 — `preflight.json`은 "검사하지 않은 것"을 반드시 담는다.**

```jsonc
{
  "schema": 1,
  "branch": "feature/plan-preflight",
  "plan_sha256": "…",          // 중복 방지 (D10)
  "scope": "topic-cluster+file-overlap",
  "verdict": "CLEAN",          // CLEAN | REJECTED | BLOCKED
  "examined": [                 // 무엇을 봤는지 (전체)
    { "kind": "topic", "label": "전화번호", "task_ids": ["3","7","11"], "result": "clean" },
    { "kind": "file",  "label": "storage.ts", "task_ids": ["3","9"],    "result": "clean" }
  ],
  "not_examined": [],           // 건너뛴 것 — 비어 있어도 필드는 존재해야 한다
  "defects": [],
  "applied": [                  // 사람이 채택해 반영한 수정 (D15)
    { "defect_id": "d1", "at": "2026-09-03T…", "sha256_before": "…", "sha256_after": "…" }
  ]
}
```

**D25 — 커버리지는 관계 단위로 센다. 태스크 단위로 세지 않는다.**

⚠️ **2026-09-03 정정. 초안(구 D18)이 틀렸다.** 초안은 이렇게 썼다:

```
not_examined = 전체 태스크  −  examined[] 에 등장한 태스크      ← 틀렸다
```

**모순의 단위는 태스크가 아니라 태스크 간 관계다.** 태스크 13개가 전부 어떤 묶음에 한 번씩
들어가면 이 차집합은 빈 배열이 된다. 그런데 **묶음 A와 묶음 B 사이의 관계는 하나도 안 봤을 수
있다.** 초안은 거짓 안심을 주는 필드를 "최악 실패의 방어선"이라고 불렀다.

관계 단위로 센다:

```
선언된 관계        = 모든 태스크의 Consumes 항목 총계          (기계가 정확히 안다)
1단계가 검사한 관계 = 선언된 관계 전부                          (기계는 빠뜨리지 않는다)
2단계가 검사한 관계 = AI 가 실제로 비교한 짝·묶음 조합
미검사 관계        = (검사 대상으로 뽑혔지만 에이전트가 죽거나 스킵된 것)
```

`preflight.json`에 `relations: { declared, examined_stage1, examined_stage2, not_examined[] }`로
남긴다. **1단계가 결정론적이라 `examined_stage1 == declared`가 항상 성립하고, 그것이 이 필드가
믿을 만한 유일한 이유다.** 2단계의 커버리지는 별도로 집계하며 완결성을 주장하지 않는다.

에이전트에게 "네가 빠뜨린 것을 보고하라"고 시키지 않는 원칙은 유지한다 — 계산은 기계가 한다.

`not_examined`가 핵심이다. **조용히 빠뜨리고 "이상 없음"이라고 하는 것이 이 기능의 최악 실패다.**
워크플로우 레퍼런스가 같은 원칙을 명시한다: *"No silent caps ... silent truncation reads as
'covered everything' when it didn't."*

**D10 — 캐시 적중 조건은 "같은 해시 + 유효한 `CLEAN`"이다. 해시 일치만으로는 안 된다.**

⚠️ **2026-09-03 정정.** 초안은 *"해시가 일치하면 검사를 건너뛴다"*였다. **직전 결과가
`REJECTED`여도 "이미 검사됨"으로 통과한다.** 결함이 있는 플랜이 캐시를 타고 게이트 ①을
지나간다 — 이 기능이 막으려던 것을 이 기능이 만든다.

```
캐시 적중 = plan_sha256 일치  AND  verdict == "CLEAN"  AND  스키마 유효
그 외 전부 = 다시 검사한다
```

`REJECTED`·`BLOCKED`·스키마 깨짐은 **재검사 대상이다.** 자동 실행(§4.1-15)의 낭비를 막는 것이
목적이지만, 낭비를 막다가 결함을 통과시키면 목적이 뒤집힌다.

**D26 — `bin/builder`가 `preflight.json`을 읽고 게이트를 기계로 강제한다.**

⚠️ **2026-09-03 추가. 초안에 이것이 없었고, 그래서 초안 전체가 강제되지 않았다.**
`controller/builder.ts:115`는 `checkHandoff()`만 부른다. `preflight` 언급이 0건이고
**`builder.ts`가 수정 대상 목록에도 없었다.** 즉 초안대로 만들면 검사를 안 돌려도, `REJECTED`가
나와도 빌드가 그냥 시작된다. "승인 전 검사"라는 주장에 강제 수단이 없었다.

`runBuilder`의 계약 검증 단계에 한 줄이 늘어난다:

| `preflight.json` 상태 | 빌드 |
|---|---|
| 없음 | **`REJECTED`** — "사전 검사를 돌리지 않았습니다" |
| `plan_sha256`이 현재 `plan.md`와 불일치 | **`REJECTED`** — "검사 후 플랜이 바뀌었습니다" |
| `verdict != "CLEAN"` | **`REJECTED`** — 결함 목록을 그대로 보고 |
| 스키마 깨짐 | **`BLOCKED`** (하드룰 #4) |
| `CLEAN` + 해시 일치 | 진행 |

이것이 게이트 ①을 "사람이 승인한다"에서 "**검사를 통과한 것만 사람이 승인할 수 있다**"로 만든다.
사람이 승인 발화를 해도 검사를 통과하지 않았으면 빌드가 시작되지 않는다.

**D11 — 워크플로우 반환값은 스키마로 검증한다. 실패는 `BLOCKED`다.**
하드룰 #4. `contract.ts`의 `checkBuildResult`와 같은 패턴이다. 이상한 값이 오면 **조용히 `CLEAN`으로
처리하지 않는다** — 검사를 안 한 것을 통과로 기록하는 것이 가장 위험하다.

**D17 — 2단계 끝에 완결성 검사관을 둔다.** 주제 묶기(1단계)는 **단일 실패점**이다 — AI 하나가
묶음을 정하고 이후 모든 검사가 그 묶음 안에서만 일어나므로, 묶기가 놓친 관계는 아무도 다시 보지
않는다. 파일 겹침(기계)이 백업이지만 §2의 대표 예시(전화번호)가 정확히 **파일이 안 겹치는** 경우다.

검사관은 계획서 전문 + 지금까지의 묶음·발견을 전부 받고 "놓친 관계가 있나"만 묻는다. 나온 것은
정상 경로(검사 → 반증)를 다시 탄다.

근거 — 워크플로우 레퍼런스의 이름 붙은 패턴이다: *"**Completeness critic:** a final agent that
asks 'what's missing — modality not run, claim unverified, source unread?'"* 그리고 문헌 실측:
에이전트가 데이터를 다 모으고도 **조립 단계에서 상호 참조에 실패**하는 것이 지배적 실패 모드
(44~47%)다. 우리 구조가 정확히 그 모양이므로 잡으려는 병에 우리가 걸릴 수 있다.

**D19 — 모든 `agent()` 호출에 `model`을 명시한다. 워크플로우 레퍼런스의 기본값을 뒤집는다.**

| 단계 | 모델 | 근거 |
|---|---|---|
| 주제 묶기 | **상급 (opus)** | 계획서 전체를 읽고 판단. 부실하면 이후 전부가 부실 (D17이 막는 그 지점) |
| 짝·묶음 검사 | 중급 (sonnet) | 짧은 텍스트 두 개 비교 |
| 반증 | 중급 (sonnet) | 동일 |
| 수정 제안 | 중급 (sonnet) | 동일 |
| 완결성 검사관 | **상급 (opus)** | 전체를 다시 보고 누락을 찾는 일 |

⚠️ **워크플로우 레퍼런스와 충돌한다.** 레퍼런스는 *"`opts.model` — 기본은 생략이며, 에이전트가
메인 루프 모델을 상속하는 것이 거의 항상 옳다"*고 한다. 여기서는 **하드룰 #3(A4)이 이긴다** —
생략하면 세션 모델을 상속하고, 이 검사기는 에이전트를 20~30개 띄우므로 티어 정책이 조용히
무력화된다. 구현자가 레퍼런스만 읽고 생략하지 않도록 이 항목을 남긴다.
최저가 티어를 쓰지 않는 이유도 레퍼런스에 있다 — *"Turn count beats token price"*, 산문 기반
작업의 하한은 중간 티어다.

### 6.4 수정 적용 — 게이트 ① 앞의 사람 결정 루프

**D12 — 적용은 검사와 분리된 별도 명령이다.** 검사가 끝나면 멈춘다. 적용은 사람이 시작한다.

```
bin/preflight <branch> --record     검사 결과 저장 → 결함 목록 출력
        ↓
  사람이 결함마다 채택 / 기각 결정          ← AskUserQuestion. 결함 하나당 하나
        ↓
bin/preflight <branch> --apply <결함 id...>   채택된 것만 plan.md 에 반영
        ↓
  plan.md 해시 변경 → D10이 재검사를 강제
        ↓
  CLEAN 이 나올 때까지 반복 → ⛔ 게이트 ①
```

**D13 — 일괄 승인을 제공하지 않는다.** "전부 적용" 버튼이 없다. 결함마다 개별 결정이다.
근거: 일괄 승인이 있으면 그것이 기본 경로가 되고, 그 순간 이 단계는 "사람이 결정한다"는
성질을 잃는다 — 하드룰 #2가 막으려던 상태로 되돌아간다. 결함이 많아서 번거롭다면
그것은 **계획서를 다시 만들라는 신호**다.

**D14 — 적용은 기계적이어야 한다.** `suggested_fix`가 담은 텍스트를 그대로 넣는다. 적용 단계에서
AI가 문장을 다시 쓰지 않는다. 사람이 승인한 텍스트와 실제로 들어간 텍스트가 달라지면 승인이
의미를 잃는다.

**D15 — 무엇을 적용했는지 남긴다.** `preflight.json`의 `applied[]`에 결함 id, 적용 시각, 적용 전후
`plan.md` 해시를 기록한다. 계획서가 왜 이렇게 바뀌었는지 추적할 유일한 기록이다 —
`git log`와 함께 두 겹이 된다.

**D16 — 적용에 실패하면 아무것도 바꾸지 않는다.** `suggested_fix`가 가리키는 위치를 찾지 못하면
(계획서가 그 사이 바뀐 경우 등) 부분 적용하지 않고 전체를 중단한다. 반쯤 적용된 계획서가
가장 나쁜 상태다.

**D22 — 매치가 여럿이면 멈추고 사람에게 묻는다.** 계획서에는 비슷한 줄이 반복된다 —
`**Files:** controller/preflight.ts` 같은 라인은 여러 태스크에 나온다. 대상 문구가 그런 구간이면
매치가 여럿이다.

**첫 번째에 조용히 넣지 않는다.** 그것은 엉뚱한 태스크를 바꾸는 것이고, D14(승인한 텍스트와
실제로 들어간 것이 같아야 한다)가 막으려던 사고 그 자체다. 후보 위치를 전부 제시하고 사람이
고른다 — 게이트 ① 앞이므로 사람이 정의상 있다 (전제 A2).

세 갈래가 전부 다르게 처리된다:

| 매치 수 | 동작 |
|---|---|

## 7. 수용 기준

### 7.1 기계적으로 검증되는 것 (`bun test`)

1. `bun test`가 통과한다. **기존 93개가 전부 살아 있다.**
2. `extractFiles()` — `**Files:**` 라인에서 경로 목록을 뽑는다. 라인이 없으면 빈 배열이며 던지지 않는다.
3. `contract.ts`가 `**Files:**` 없는 할 일을 계약 위반으로 잡는다.
4. `overlappingPairs()` — 같은 파일을 건드리는 짝만 반환한다. 자기 자신과 짝짓지 않는다. 순서가
   뒤집힌 중복(3×7과 7×3)을 만들지 않는다.
5. `checkDefects()` — 스키마에 맞지 않는 입력에 `BLOCKED`를 낸다. **빈 배열은 유효한 입력이며
   `CLEAN`이다** (결함 없음과 검증 실패를 구분한다).
6. `preflightVerdict()` — 결함이 하나라도 있으면 `REJECTED`.

### 7.1.2 1단계 기계 검사 (2026-09-03 추가 · D6 · D25 · D26)

23. `parseInterfaces(task)` — `**Interfaces:**`의 `Consumes`/`Produces`를 뽑는다. `from Task N`의
    N을 분리한다. 섹션이 없으면 빈 결과이며 던지지 않는다.
24. `extractFiles(task)` — **멀티라인 `- Create:` / `- Test:` 형식**을 파싱한다 (D6). 한 줄 CSV가
    아니다. 백틱을 벗긴다. 파일 시스템을 건드리지 않는다 (D21).
25. `danglingRefs(tasks)` — `X from Task N`을 소비하는데 Task N의 `Produces`에 X가 없으면 결함.
    Task N이 아예 없는 경우도 같다.
26. `orderViolations(tasks)` — 앞 태스크가 뒤 태스크의 산출을 소비하면 결함.
27. `signatureCandidates(tasks)` — 같은 심볼의 `Produces`/`Consumes` 서명이 텍스트로 다르면
    **결함이 아니라 후보**로 낸다. `stage: 2`로 넘긴다.
28. 위 셋이 낸 `PreflightDefect`는 `task_ids`가 **항상 2개 이상**이고 `relation`이 채워져 있다
    (D27 — 타입이 강제한다).
29. `relationCoverage(tasks, examined)` — 선언된 관계 수와 검사된 관계 수를 센다.
    **1단계만 돈 경우 `examined_stage1 == declared`가 성립한다** (D25).
30. **게이트 강제** — `runBuilder`가 `preflight.json` 없음 / 해시 불일치 / `verdict != CLEAN` 에
    각각 `REJECTED`를 내고, 스키마 깨짐에 `BLOCKED`를 낸다 (D26). **빌드가 시작되지 않는다.**
31. `--record`가 `preflight-raw.json`의 `plan_sha256`이 현재 `plan.md`와 다르면 `BLOCKED` (D28).
32. `--record`가 기존 `preflight.json`의 `applied[]`를 **읽어 이어붙인다.** 재검사 후에도 이전
    적용 기록이 남아 있다 (D29).
33. `findFixSites`는 **해당 태스크 본문 안에서만** anchor를 찾는다 (D24). 다른 태스크의 같은
    줄에 매치되지 않는다.

### 7.1.1 엣지 케이스 (전부 던지지 않고 우아하게 끝나야 한다)

| # | 상황 | 기대 동작 |
|---|---|---|
| E1 | 태스크가 1개뿐 | 짝 0개. `CLEAN` + `examined[]`에 그 태스크 1건. 던지지 않는다 |
| E2 | 같은 태스크가 같은 파일을 두 번 적음 | 중복 제거. 자기 자신과 짝짓지 않는다 |
| E3 | `**Files:**` 라인은 있는데 값이 비어 있음 | 빈 배열. 계약 위반은 `contract.ts`가 따로 판정한다 |
| E4 | `plan.md`가 아직 없음 (훅이 먼저 발동) | `--gate`가 조용히 종료 코드 0. 오류가 아니다 |
| E5 | 워크플로우가 중단됨 (사람이 취소) | `--record`에 입력이 없다 → **`BLOCKED`**. `CLEAN`으로 처리하지 않는다 (하드룰 #4) |

E5가 중요하다. **검사를 안 한 것과 검사해서 깨끗한 것은 다르다.** 입력이 없을 때 `CLEAN`을
내면 게이트 ①에서 사람이 "검사 통과"로 읽는다.

### 7.2 픽스처로 검증되는 것

7. **모순이 있는 계획서** 픽스처(§2의 전화번호 예)를 넣으면 `REJECTED`가 나오고, `defects[]`에
   해당 두 할 일의 id가 담긴다.
8. **모순이 없는 계획서** 픽스처를 넣으면 `CLEAN`이 나오고, `examined[]`가 비어 있지 않다.
9. 캐시는 **`CLEAN`일 때만** 적중한다 (D10). 해시가 같아도 `verdict`가 `REJECTED`·`BLOCKED`거나
   스키마가 깨졌으면 `--gate`가 **재검사를 요구한다.** 해시 일치만으로 통과시키면 결함 있는
   플랜이 캐시를 타고 게이트를 지나간다.
9-1. 해시 일치 + `CLEAN`일 때 `--gate`는 "이미 검사됨"으로 종료 코드 0으로 끝나며 에이전트 단계로
   넘어가지 않는다.
10. `not_examined` 필드는 비어 있더라도 **항상 존재한다.**
10-1. `notExamined(tasks, examined)` — 전체 태스크에서 검사된 것을 뺀 차집합을 낸다.
   `examined[]`가 비면 전체 태스크가 나오고, 전부 검사됐으면 빈 배열이 나온다. **에이전트
   보고를 신뢰하지 않고 기계가 계산한다** (D18).
11. `--apply d1` 은 결함 `d1`의 `suggested_fix` 텍스트만 `plan.md`에 넣는다. 다른 결함은 반영되지
    않고, 넣은 텍스트는 `suggested_fix`와 **바이트 단위로 동일**하다 (D14).
12. `--apply` 가 대상 위치를 찾지 못하면 **`plan.md`를 전혀 건드리지 않고** 0이 아닌 종료 코드로
    끝난다 (D16 — 부분 적용 금지).
13. `--apply` 성공 후 `preflight.json`의 `applied[]`에 항목이 하나 늘고, `sha256_before`가 적용 전
    해시와, `sha256_after`가 적용 후 해시와 일치한다.
13-1. `findFixSites(planText, defect)` — 매치 위치 목록을 낸다. **0개 / 1개 / 2개 이상 세 갈래가
    각각 다르게 처리된다** (D22). 2개 이상일 때 `--apply`는 `plan.md`를 건드리지 않고 후보
    목록을 내며 종료 코드로 "사람 선택 필요"를 알린다. 첫 번째를 조용히 고르지 않는다.

### 7.3 사람이 확인하는 것

14. `plan.md`를 저장하면 형식 검사가 자동으로 돌고, 내용 검사가 필요하면 알림이 뜬다.
15. 검사 결과 화면에 **무엇을 봤는지**가 나온다 (묶음 목록 + 결과).
16. 결함이 있으면 **고칠 방법이** 제시되고, 그 안에 **계획서에 그대로 넣을 텍스트**가 들어 있다.
17. 결함마다 **채택할지 기각할지 하나씩 물어본다.** "전부 적용"은 없다 (D13).
18. 채택한 것만 `plan.md`에 반영되고, **기각한 것은 반영되지 않는다.**
19. 반영된 텍스트가 **내가 승인한 텍스트와 글자 그대로 같다** (D14 — 적용 단계에서 AI가 문장을
    다시 쓰지 않는다).
20. 반영 직후 **자동으로 다시 검사한다** (고친 것이 새 모순을 만들 수 있으므로).
21. 아무것도 채택하지 않으면 **`plan.md`는 전혀 바뀌지 않는다** — 검사 전후 파일 해시가 같다.
22. `preflight.json`을 열면 **무엇이 언제 반영됐는지** 남아 있다 (D15).
